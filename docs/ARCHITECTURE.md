# 工作架构重构 v1（草案）

日期：2026-11-16 · 状态：待确认分叉 · 不对应任何已实现代码

---

## 0. 一句话结论

现在这套东西是**三个脚本 + 一堆文件**，能跑，但不是架构。
病根只有一个：**同一件事实被写了三遍**（`_graph.json` 存状态、`notes.jsonl` 存叙事、`ledger.jsonl` 存动作），三处必然漂移。
重构的方向：**事件日志做唯一真源，状态是投影**。

---

## 1. 七问现状（据实证，不美化）

### 1.1 画布有吗

有，但是**死的**。

| | 现在 |
|---|---|
| 产物 | `assets/<项目>/_canvas/project-flow.svg` + `.mmd` |
| 生成方式 | `project_flow.py canvas` 一次性渲染 |
| 能看 | 能，九泳道 + 箭头 + 四色状态 |
| 能点 | 不能。方块没有 id，点了没反应 |
| 能改 | 不能。改的是源数据再重渲染 |
| 语义 | 这是一张**渲染出来的图**，不是画布 |

画布的定义是「有实体、有 id、可增删、可交互」。按这个标准，我们现在是 0。

### 1.2 事件 Agent 怎么激活

**不存在。** 现在只有两件事：

- MCP 工具被**人**调用（ChatGPT / Claude / Cursor 里人发话）
- `cron` 到点跑 `push.py`，是**脚本**在跑，不是 agent 在判断

没有"什么时候该自己动"的定义，所以没有事件 Agent。这恰恰是最该补的一层，见 §3.4。

### 1.3 记账台是怎样的

现在是**一条混装流水**：

```
state/ledger.jsonl     assets.write / note.append / condition / push 全塞一起
notes/notes.jsonl      7 种 kind（decision/condition/intent/todo/open/note/push）
```

问题：
- 无法回答"这个决定是谁改的、凭什么改的"
- 无法回答"我们对外答应过什么"——**承诺账缺失**，而这是最不可逆的
- 日志是给人看的文本，机器没法拿它重建状态

### 1.4 设计版本回溯和复盘

**回溯：没有。** 改三次只留最后一条文字，`_graph.json` 被原地覆盖。
**复盘：没有。** 没有事件流，就没有"当时怎么想的"，只有"现在是什么"。

唯一靠得住的是 `sha256_16`，但它只证明"文件变了"，不证明"为什么变"。

### 1.5 事件成立条件 / 设计思考 / 问题推演 / 处理 / 推送

- **成立条件**：没定义。现在任何调用都写一行日志，噪音和事实混在一起。
- **设计思考**：散在 `notes` 的 `intent` 里，没绑到具体决策，读不出推理链。
- **推演**：**没有**。`set` 直接改真源，错了只能靠文字描述回滚。真正的推演应该"算完不落盘"。
- **问题处理**：没有 `issue` 这个实体，问题只活在对话里。
- **推送**：只是通知（状态快照），不是提议。人收到后要自己决定做什么，AI 没有给出"我建议做 X，你点头"。

### 1.6 人与 AI 怎么分工、AI 处理哪些内容

**没写死，所以每次临场判断。** 现在靠人格卡里几句"不替你拍板"，属于软约束，不是架构。

## 2. 病根（三条）

1. **多真源**：状态 / 叙事 / 动作三套，谁也说不清哪个准。
2. **无实体 id**：交付物有 `CD-100`，资料只有路径。路径一改，引用全断；同一个对象在三个文件里三种写法。
3. **时间是隐含的**：没有版本、没有 as-of 查询。"上周净高多少"答不了，"如果当时不改会怎样"更答不了。

---

## 3. 重构：三层

```
┌─ 交互层 ─────────────────────────────────────────────┐
│  委托 / 提案 / 回执 / 问题单                           │
│  人只做两件事：确认、判断。其余都是提案                 │
└──────────────────────┬───────────────────────────────┘
                       │ 只能通过 append(event) 写入
┌─ 事件层（唯一真源）──────────────────────────────────┐
│  events.jsonl  append-only  每条带 subject/actor/    │
│  evidence/effect/caused_by                            │
└──────────────────────┬───────────────────────────────┘
                       │ fold(events) 可重放
┌─ 投影层（可丢弃、可重建）────────────────────────────┐
│  状态投影：现在的依赖图 / 谁卡谁                       │
│  账本投影：变更账 / 承诺账 / 动作账                     │
│  复盘投影：决策路径 + 因果链                           │
│  画布投影：带 entity id 的 SVG（可点，不可自由编辑）    │
└──────────────────────────────────────────────────────┘
```

一句话：**投影随时可以删掉重建，事件不能。**

### 3.1 事件 schema

```json
{
  "eid": "e000123",
  "ts": "2026-11-16T18:04:00-08:00",
  "type": "condition.changed",
  "project": "演示项目",
  "subject": "cond:S-200.clear",
  "actor": { "kind": "human", "id": "carl", "disc": "structure" },
  "evidence": { "kind": "doc", "ref": "S-200 结构复核单", "loc": "2026-11-15 / p2" },
  "payload": { "from": "3200mm", "to": "2850mm", "reason": "梁高复核" },
  "caused_by": ["e000101"],
  "effect": { "invalidated": ["M-300", "I-200", "L-100"] }
}
```

### 3.2 事件类型（先定 12 个，不再多）

| 类型 | 作用 |
|---|---|
| `condition.fixed` / `condition.changed` / `condition.reopened` | 条件三态 |
| `deliverable.issued` / `deliverable.invalidated` / `deliverable.reopened` | 交付物三态 |
| `material.locked` | 材料锁定（锁定后不得擅自换材） |
| `decision.confirmed` | 人拍板，**唯一能锁死方向的类型** |
| `issue.opened` / `issue.closed` | 问题单 |
| `doc.ingested` | 资料入库（带原文 hash 与出处） |
| `proposal.created` / `proposal.accepted` / `proposal.rejected` / `proposal.expired` | 人机交互 |
| `push.sent` / `push.seen` / `push.acted` | 推送与回执 |
| `snapshot.created` | 快照锚点 |
| `revert.applied` | 回滚（不删原事件，补一条反向事件） |

### 3.3 事件成立条件（四要素，缺一不入账）

必须同时有：

1. **subject** —— 作用在哪个实体上（必须是有 id 的实体，不能是"那个座椅方案"）
2. **actor** —— 谁做的（human / agent / 系统），agent 必须带 `on_behalf_of`
3. **evidence** —— 出处。文件+行号 / 邮件 id / 会议时间戳 / 复核单号。**空字符串不合法**
4. **effect** —— 改变了什么状态。说不出改变了什么，就不是事件

不满足的，降级为 `comment`，不入主日志，不参与投影。
判据：**"如果这条丢了，会不会有人做错事？"** 会，才是事件。

### 3.4 事件 Agent 怎么激活（四类触发）

| 触发 | 时机 | 允许的动作 | 首版口径 |
|---|---|---|---|
| **材料到达** | 新文件入库 | 抽取 → 比对已有条件 → 发现矛盾 → 建 issue | 开 |
| **条件变更** | 任意 condition.* 事件 | 算失效面 → 生成 proposal | 开 |
| **时间** | 每天一次 | 逾期项 → proposal（催办） | 开 |
| **人招呼** | MCP 调用 | 任意只读；写入需提案 | 开 |

硬约束：
- 触发只产生 **proposal**，不直接改状态
- 每个项目每天最多 3 条主动消息（沿用现有上限）
- 同一 proposal 24h 不重复
- 触发器的规则本身写在 `triggers.yaml`，可 diff、可 review，不埋在代码里

### 3.5 提案（替代现在的"推送"）

推送是通知，提案是**带预设动作的请求**。三档：

| 档 | 形态 | 例子 |
|---|---|---|
| `info` | 只告知，不需回应 | 「结构复核单已入库，涉及 3 个条件」 |
| `suggest` | 建议一个动作，一键采纳 | 「按新梁高，M-300 需重排，建议今天出图」 |
| `act` | 已代做，待确认或撤回 | 「已起草变更单 v1，确认后发」 |

每条提案必须有：`what`（做什么）、`why`（因为哪条事件）、`cost`（代价/影响面）、`expire_at`（默认 72h）。
**沉默不等于同意**：到期自动 `proposal.expired`，不执行。

### 3.6 记账台（三本账，都从事件投影）

| 账 | 回答什么 | 来源事件 |
|---|---|---|
| **变更账** | 谁在什么时候把什么从 A 改成 B，凭什么 | condition.* / deliverable.invalidated |
| **承诺账** | 我们对外答应过什么，是否已兑现 | decision.confirmed / push.acted |
| **动作账** | AI 做了什么，谁授权，怎么撤 | proposal.accepted / agent.* |

承诺账单独成册，因为文档 §11 那句：已发出的承诺、已下单材料、现场已完成工作，**恢复画布消除不掉**。

### 3.7 版本回溯与复盘

- **快照**：每 50 条事件或每天一次，存 `state-<ts>.json` + 事件序号 + sha256
- **回溯**：`rewind --to <ts>` → 从最近快照重放，生成新状态；同时补一条 `revert.applied` 事件。**不删历史。**
- **推演（what-if）**：`simulate --set S-200.clear=2850` → 内存重放，输出失效面，**不落盘、不写事件**
- **复盘**：按 `caused_by` 拉因果链，输出「决策路径图」；人给每条 decision 打 `outcome: good/bad/unclear`，这是唯一能让系统学会判断的字段

## 4. 人机分工

### 4.1 AI 处理什么

抽取（文档→条件/决定）、比对（新资料 vs 已有条件）、归因（谁卡谁）、算影响面、起草（变更单/纪要/提案）、检测失效、汇总、排优先级、准备选项。

### 4.2 人处理什么

审美判断、规范豁免、取舍、对外承诺、签字、下单、删除、改已确认决定。

### 4.3 三条契约

1. **AI 只出提案，不出决定。** 提案必须有预设动作和代价。
2. **人的确认是一条事件**（`decision.confirmed`），不是聊天里一句"嗯"。
3. **不可逆动作（对外发送、下单、删除）永远 `act` 档，需显式确认，且进承诺账。**

## 6. 待定的三个分叉（决定架构走向）

### A. 画布：投影式 还是 可编辑

- **A1 投影式**（推荐）：SVG 节点带 entity id，可点开看事件流，不可自由拖拽。2 周。
- **A2 引入 tldraw / Excalidraw** 做真画布：多 3–4 周，且要解决"画布对象 ↔ 交付物"双向映射。

### B. 事件粒度

- **B1 交付物级**（推荐）：一条事件 = 一个交付物状态变化。事件少、易复盘。
- **B2 对象级**：细到每张便利贴/每根管线。接近 Miro，但事件量 ×50，单人跑不动。

### C. 单机 还是 多人

- **C1 单人先跑**：无权限层，省 30–40 人月。
- **C2 直接上 provenance**：摘要继承来源可见性、对象级 ACL。多人必需，但会把 P0 拖长一倍。

**我的建议：A1 + B1 + C1，先把事件层立稳。** 三层里只有事件层是不可逆的投入，画布和权限都可以后补。

## 7. 这份文档没解决的

- 冲突检测（几何/规范）不在架构内，它是另一个引擎。
- 外部渠道（邮件/Teams/企微）只到"归一化成事件"，没设计入站网关。
- 多项目/多团队的事件隔离，只写了 `project` 字段，没设计租户边界。

**四要素校验是真的会拦**：`event_set` 缺 evidence 直接返回错误，不写盘。

### 8.2 MCP 已挂（22 个工具）

事件层 5 个：`events`（查流）、`event_set`（改写+传播，强制 evidence）、`simulate`（推演）、`accounts`（三本账）、`rewind`（回滚）。

触发层 2 个：`proposals`（`action=list` 列未结，`action=scan` 跑规则，`dry` 只预览）、`proposal_act`（`decision=accept|reject`，驳回必须给 note）。scan 在 MCP 里调用时 stdout 被重定向捕获，不会污染 JSON-RPC 通道。

旧 `flow_set` 保留兼容，但**新代码一律走 `event_set`**——`flow_set` 直接改 `_graph.json`，绕开了事件层。

### 8.3 尚未实现（下一批）

1. **复盘 outcome 标注**：`decision.confirmed` 已入库，但没有 `outcome: good/bad` 的写入路径——复盘现在只能看因果链，不能判好坏。
2. **自动快照**：现在手动跑，没挂到 cron。
3. **push.py 退役**：它还在按自己的指纹直接发系统通知，没走 `proposal` 通道，等于两套打扰逻辑并存。下一步只保留一条：push 读未结提案，不自己算。
4. **flow_set 退役**：仍直改 `_graph.json`，留着只为兼容老命令。

### 8.4 一个语义边界要记住

B1 是交付物级：**只对已出（issued）的交付物算返工**。
所以同一条条件改第二次时，返工数会变 0——不是 bug，是下游已经 stale。
CLI 和 MCP 都会返回 hint 说明这一点。


### 8.5 触发引擎（2026-11-17 实测）

规则在 `triggers.yaml`，代码在 `bin/trigger.py`，状态在 `state/trigger_state.json`。五条规则：`rework-after-change`（suggest）、`blocked-too-long`（suggest）、`ready-idle`（info）、`material-arrived`（info）、`promise-stale`（act）。

实测记录：

| 动作 | 结果 |
|---|---|
| `ingest structure/S-200_结构复核单.md` | 写 `doc.ingested`，sha `ff9713a8…` |
| `trigger.py scan` | 2 条提案：p0001（6 项返工，suggest）、p0002（新资料，info） |
| 再扫一次 | 0 条，两条都命中 cooldown（0.0h） |
| 清指纹 + `max_per_day: 2` + 已用 2 | 0 条，输出「超出今日 2 条上限」 |
| `accept p0001 --note` | 写 `proposal.accepted`，**不进承诺账**（suggest 档） |
| `proposal_act reject p0002`（走 MCP） | 写 `proposal.rejected`，`verify` 双跑一致 |

三条纪律在代码里是硬的：静默时段（23–8 点）只把提案标 `hold: true` 入库、不发送；沉默不等于同意，`expire_at` 到点自动写 `proposal.expired`；提案本身不改任何状态，采纳之后仍要单独调 `event_set` 才算改。


### 8.6 复盘审查（2026-11-17）

四个真问题，详见根目录 `复盘审查-2026-11-17.md`。要点：

1. **P0 二次变更完全沉默**：`candidate_rework` 在 `len(affected)==0` 时直接返回，等于把「返工集为空」当成「无变化」。修：出 info 档「条件又变了」，指纹改记触发事件 eid。
2. **P0 改历史不留痕**：`hash`/`hash_prev` 写了但从不校验，`verify` 只比事件投影 vs `_graph.json`（同源）。修：`check_chain()` 逐条重算 + 成链核对，接进 `verify`；本项目「链校验 通过」，篡改测试当场报「e000051 内容与哈希不符」。
3. **P1 `hold` 是死字段**：静默时段入库的提案没人发。修：`trigger.py digest`（MCP `proposals{action:"digest"}`）。
4. **P2 指纹无老化 / 抬头口径含糊**：保存时按 48h 清，抬头改「今日额度 n/3（含本次）」。

尚未修：复盘 outcome 写入路径、`push.py` 与提案两套打扰逻辑并存、`flow_set` 绕事件层、accept 后无重出追踪。


### 8.7 复盘闭环（2026-11-17）

复盘要能成立，缺的从来不是「回顾页面」，是**一条决定后来对不对，有没有人写下来**。补了四件：

| 件 | 位置 | 作用 |
|---|---|---|
| `decision.reviewed` 事件 | eventlog TYPES | 给某条决定标 `outcome: good|bad|unclear` + 备注 + 距今天数 |
| `review <eid> --outcome …` | `eventlog.py` | 写入路径；已复盘的不许重复标（`--force` 才覆盖，会留两条） |
| `reviews` | `eventlog.py` | 复盘台：待复盘（超 7 天标红）/ 已复盘 / 命中率 good:bad |
| `decision-unreviewed` 规则 | `triggers.yaml` | 超过 N 天没复盘的决定，由触发引擎出声催，而不是靠人记得 |

承诺账现在每条决定后面都带结果：`｜结果 **good**（0.5 天后）` 或 `｜**未复盘**`。

实测：`review e000049 --outcome good --note "现场放样后通视成立，断档 520mm"` → 承诺账显示 `结果 good（0.5 天后）`；再标一次被拒；沙盘造一条 9 天前的决定，`decision-unreviewed` 当次出提案「1 条决定超过 8 天没复盘」。MCP 侧 `decision_review{action:list|review}` 同步可用。

一条边界：`outcome` 只能人给。AI 可以提示「这条该复盘了」，但不能替人说「当时那样做是对的」——那是判断，不是记录。


### 8.8 推送合并进提案通道（2026-11-17）

v0.1 的 `push.py` 自己算指纹、自己排优先级、自己判每日上限，与 `trigger.py` 的提案通道并行。两条路各算一遍「该不该出声」，短期看不出问题，长期必然分裂成「提案里没有、手机却响了」。

现在按「判」与「送」切开：

| 层 | 负责 | 不负责 |
|---|---|---|
| `trigger.py` | 六条规则、冷却、每日上限、静默时段判定、带 tier/why/expire_at 出提案 | 怎么送到人 |
| `push.py` | 挑 `status=created` 且不在 `push.sent.pids` 的提案、合成一条、弹一次、落 outbox | 要不要出声 |

三个判据：

- **幂等靠 pids，不靠指纹**。指纹回答「事实变没变」，送达回答「这条送没送过」，两件事不能共用一个机制。
- **静默时段不销毁提案，只延后送达**。`hold=true` 的提案在 push 里进积压，早上照发；不是丢弃重生成，否则每天早上都要重新过一遍规则，还会撞配额。
- **一条消息一次弹**。多条合并，超 3 条截断，宁可让人点开看，也不刷屏。

实测（沙盘「推送测试」）：2 条送达 + 系统通知「已发出」+ 落盘 outbox；重跑「（没有可发提案）」；还原 `quiet_hours [23,8]` 后新建提案 `hold=true`，push 输出「（没有可发提案）；静默时段积压 1 条」。沙盘已清理，真项目 75 条事件、链校验通过。

仍未做：cron 行（`30 9 * * *` 写在 README 里但没装进系统）、`flow_set` 仍绕过事件层、提案被 accept 后无「重出追踪」。


### 8.9 重出追踪：pid 与问题身份分开（2026-11-17）

原来的毛病：提案 accept 之后，同一条规则过几天又提同一件事，看起来和一条全新提案一模一样。人没法判断「这是新问题，还是上次那招没管用」。

根子在于只有一种身份——`pid`，那是「一次提」的编号，不是「一个问题」的身份。补一个 `problem_key`：

| 规则 | problem_key |
|---|---|
| rework-after-change | `rework:<条件 subject>`（同一条件再变就是复发） |
| blocked-too-long | `blocked:<条件 id>` |
| ready-idle | `ready:<最老可开工交付物的末条事件>` |
| material-arrived | `doc:<文件 sha256 前 16>` |
| promise-stale | `promise:<决定 eid>` |
| decision-unreviewed | `review:<最老待复盘决定 eid>` |

扫描时按 `problem_key` 查历史回合，算出 `round`（第几次）与 `recurrence`（上次哪条、什么结果）。`round` 同时进指纹，所以复发不会被冷却误挡——冷却挡的是「同一回合重复提」，不是「问题又来了」。

`trigger.py list` 会写出来：

```
p0004 [信息] created  条件又变了：梁底净高（下游已 stale，无需重复返工）
    ↻ 复发第 3 次｜上次 p0003 是 rejected｜上次被驳回过，这次有新证据才再提
    到期 2026-11-20T07:41｜原因 e000082｜问题 rework:cond:S-200.clear
```

上次若是 accepted，提示换成「上次已采纳，说明做法没落地，或这条规则太宽」。**这是两种完全不同的处置**：前者要追执行，后者要改规则。以前这两种情况长得一样。

`trigger.py trace <pid>` 给一个问题的完整履历（三回合、每回合的结论与备注），MCP 侧走 `proposals{action:"trace", pid}`。

实测（沙盘「复发测试」）：scan → p0001 → accept → 同条件再改 2800→2760 → 复发 scan 出 p0003 标 `↻第2次（上次 p0001 accepted）`；reject p0003 后再改 → p0004 标 `↻第3次（上次 p0003 rejected）`；`trace p0001` 列出三回合与判读「还有未结的一回合」。沙盘已清，配置已还原，真项目 75 条事件不变。

**顺手抓到一个真 bug**：`apply_event` 里 proposal 分支用的是字段白名单，`problem_key` 不在白名单里 → 事件写了、投影没存 → `round` 永远算 1，复发追踪形同虚设。改成全量搬运（除 id/note 外全带），以后加字段不会再静默丢。

边界：本节只回答「问题又冒出来了没有」。**不回答「采纳之后问题解决了没有」**——那需要解决证据（`issue.closed`、该交付物重新 `issued`），还没做。现在的 `trace` 只能把回合摆出来，判断仍在人。


### 8.10 收尾两件：退役 flow_set、装上定时（2026-11-18）

**一、`flow_set` 退役**

它原来直接改 `_graph.json`，绕开事件日志。只要有人走一次这条路，同一条事实就有两份记录，而且分不出谁在后——`rewind` 之后那次改动会凭空消失，台账里查不到。

处理方式不是删工具（旧提示词还在调它），而是让它必须给 `evidence`，内部转发到 `eventlog.change_condition`：

- 有 evidence → 正常改，写事件，再把投影回写 `_graph.json`
- 无 evidence → 拒绝，并说明「换 event_set，或直接改图纸——但那样不进历史」
- CLI 侧 `project_flow.py set` 同样退役，只有 `--legacy` 才走老路（留给修历史数据）

**二、定时装上**

launchd 而非 cron：`~/Library/LaunchAgents/com.carlz.workbench.push.plist`，每天 09:30 `push.py run`，日志进 `state/logs/push.{out,err}.log`。选 launchd 的理由是笔记本休眠后 cron 会漏、launchd 醒后补跑。

**过程中抓到两个真 bug**

1. **改成本来值也写事件**。`change_condition` 不判等，`2700mm → 2700mm` 照样落一条 `condition.fixed`。沙盘里连写三条同样的值，台账立刻变成噪音，`rewind` 的目标也变得不可判。现在值相同且状态相同直接拒：「值没变：X 已是 N（fixed）。要留痕请写 comment，不要造一条空变更」。
2. **CLI 参数位置错了**。`push.py` 把 `--project` 定义在主 parser 上，但 README 与 plist 都写成 `run --project X`（子命令在前）→ argparse 报 `unrecognized arguments`，launchd 任务退出码 2。修法子命令也接受 `--project`（`default=SUPPRESS`，不覆盖主 parser 的值），现在两种写法都通。

第 2 条值得记一笔：它在交互式测试里永远不会暴露，因为我手敲的一直是 `--project X run`。是 launchd 按文档原样执行才把它逼出来的——**文档里的命令要原样跑一遍**，否则文档和代码各错一半，合起来看着都对。

实测：`flow_set` 无 evidence 被拒并指向 `event_set`；有 evidence 时写入 `e000079`、`_graph.json` 同步到 `2650mm`、`affected` 为空（下游本就 stale）；`launchctl kickstart` 后 `runs = 2 / last exit code = 0`，日志「（没有可发提案）」；`calendarinterval` 显示 Hour 9 / Minute 30。沙盘已清，真项目 75 条事件不变。

## §8.11 从零建项目与条件表起草（2026-11-18）

### 为什么要这一节

在此之前，`migrate` 是唯一入口：它把一份**已经写好值的** `_graph.json` 搬进事件流。
真实项目没有那份文件，而人不会为了用工具先画一张结构图。所以第一个门槛不是功能，
是「第一个条件怎么进来」。

### 两个入口分工

| 命令 | 用途 | 是否带值 |
|---|---|---|
| `eventlog.py bootstrap` | 从模板声明结构：9 专业、16 条件占位、19 交付物 | 否，全部 `open` + 空值 |
| `eventlog.py migrate` | 把已有 `_graph.json` 平移进事件流（含值） | 是 |

bootstrap 一个值都不填——这是刻意的。模板只保证「问对了问题」，不保证答案。

### 起草器的三条纪律（代码里强制，不靠自觉）

1. **起草器绝不写 `fixed`**。它只写 `state/drafts/*.json`，状态 `proposed`。
   入账唯一路径是 `draft.py confirm`，而 confirm 必须以人的身份调用（`--by`）。
2. **每条候选带出处**：`文件名:行号` + 原句。无出处的推断不进表。
3. **同条件两值 → conflict**：默认拒写，逼人先定一个；若其中一条名称与模板完全一致，
   它为正主，其余「撞名但模板没有」的降级为新建条件（例：石材供货周期 ≠ 石材样板确认周期）。

### 起草器能做什么、不能做什么

能做：`- [专业] 名称 = 数值单位` 的精确行；散话里「名称 + 数字单位 + 专业关键词」的句子（低置信）。
不能做：理解烂散文。真会议纪要写「王工说那个梁底下大概能给您留两米八」——它提不出来。
这一档要么让模型读，要么人用 `event_set` 手录。**不要假装它懂。**

### 确认卫生

每条确认记 `latency_s`（草稿创建 → 本条确认）。`draft.py stats` 输出中位数与「<2 秒」占比。
零秒占比高不是效率，是橡皮章的证据——这是唯一能事后发现「AI 提的、人没看」的仪表。

### 实测（2026-11-18 · 示例项目）

- bootstrap：41 条事件（16 条件 + 19 交付物 + 6 条 change），链校验通过，双跑一致。
- 起草：9 条候选（6 条精确行、3 条散话），其中 4 条与现状一致标 `=`、5 条待确认。
- 确认 4 条 → 变更账 4 行，全部带 `文件:行号`；`draft.py stats` 中位数 14 秒、零秒 0 条。
- 改值路径：`2850mm → 2800mm` 写入 1 条 `condition.changed`；该项目无 issued 交付物，
  返工 0 → 触发引擎按 P0-1 修复后的语义出 **info 档**「条件又变了：梁底净高（下游已 stale，无需重复返工）· 2850mm → 2800mm」。
  **这一条是修复之后第一次在非沙盘项目上得到验证。**

### 顺手修掉的两个老 bug

1. `workbench_mcp.py` 在 stdout 打印启动横幅 —— MCP stdio 协议要求 stdout 只有 JSON，
   严格的客户端会直接解析失败 → 改到 stderr。
2. `eventlog.py` / `draft.py` / `trigger.py` 的主 parser 选项只认子命令之前，
   而文档与 plist 都写成 `cmd --project X` → argparse 报 `unrecognized arguments`。
   统一用 `eventlog.normalize_argv()` 把顺序摆正，不再给每个子命令复制一份 `--project`。

### 仍是空的

- `flow_set` 已退役（必须给 evidence），但历史项目里它写过的记录不会自己补出处。
- 采纳后的解决证据（issue.closed / 重新 issued）仍缺，`trace` 只到「上次采纳了」为止。
- `push.seen` 回执仍缺。

## §8.12 变更清单解析器（2026-11-18 · 真实变更单实测）

第一份真实材料是一份 10 页、中英对照、9 个事项的《设计修改事项及审核安排》。
拿条件起草器跑它，只出 2 条垃圾候选——因为它不是「名称 = 数值」，是「事项 + 节点 + 前提」。
所以加了 `bin/changelog.py`，两个解析器分工固定：

| 资料形态 | 解析器 | 产出 |
|---|---|---|
| 交底/纪要里的「名称 = 数值单位」 | `draft.py` | 条件候选 → 人确认 → `condition.fixed` |
| 一页一条的变更/审核安排 | `changelog.py` | 变更事项 → 1 交付物 +（文档写了才有）1 前提条件 |

### 三条实现判断

1. **相对时间必须换算，且必须标「推算」**。文档写「下周一」，没有年份月份。
   规则：文档日期之后最近的周一为下周起点。`TBC` 与未写一律留空，不猜。
   所有由推算得到的节点，提案里的 why 都写明「非原件明写」——否则会被当成承诺。
2. **「文档没写前提」不等于「前提未定」**。只在文档明写「需先…」「面积待…」时才建 open 条件；
   没写就 requires 为空，交付物直接进 ready。第一版我给 9 条都建了前提，结果 9 条全 blocked——
   那是我替文档编了 7 条不存在的前提。
3. **原因句要挑「像结论」的那句**。中英对照会混入英文长句与「提交…供审核」这种流程句。
   判据：中文占比 ≥0.3、以句号收尾、不含「审核/提交」。这条改了两轮才对上
   （02 的原因最初取成了「提交排风调整方案供审核。」）。

### 顺带修掉的一个真 bug

**冷却记忆比事件流活得久**：项目重建后事件流清空，`trigger_state.json` 里的指纹还在，
新提案被「冷却中」挡掉，而它指向的提案已经不存在。修法：指纹条目从裸时间戳改为
`{ts, pid}`，扫描时若该 pid 已不在提案表里，视为孤儿冷却并清除（老格式无法判定，保持原行为）。

### 实测结果（示例变更单项目：48 事件、17 条件、28 交付物、链校验通过）

- 9 条事项全部入账，每条带页码出处；CHG-03 因文档明写「需先与厂家沟通并与幕墙顾问确认」而 blocked，其余 8 条 ready。
- 4 条节点已过 7–9 天（CHG-02/05/04/06），台账里没有任何 `deliverable.issued` →
  触发引擎出 suggest 档：「是已提交没登记，还是确实晚了？」——只能问，不能断言。
- 走了一次真实驳回：p0001 因 why 为空被驳回，补页码后重出 p0002 标「↻第2次｜上次 rejected」。

### 仍缺

- 文档只给「方案提交」，没有「审核通过」这一侧的时点；审核结论要人补。
- `13㎡ → 50㎡` 这类变更当前只存成原因文字，没有落成 `condition.changed` 的结构化值。下一步。

## §8.13 一天一条：`bin/day.py`（2026-11-18）

四个 Agent 的分工已经能跑，但**调度还是人**：draft → confirm → scan → push 四步要手动敲。
`day.py` 不新增智能，只把「该看的」收敛成一条消息，并守住一条边界：**它不写任何业务事件**。

| 动作 | 谁做 | 说明 |
|---|---|---|
| 扫新资料、解析成草稿 | day（= 事件 Agent 的前半段） | 只落 `state/drafts/`，未确认不算账 |
| 触发扫描 | day 代为调用 trigger | 提案照旧受冷却/上限/静默约束 |
| 排成一条 | day | 三段：待确认候选 / 提案 / 解析没结果 |
| 确认、接受、驳回 | 人 | 一条命令或一句话 |

`--all` 把全部项目合成一条，安静的项目只在末尾列名，不占版面。

### 做的时候撞到的三个真问题（都改了代码，不是改文案）

1. **同一份资料有多份解析结果时，取到了最早那份**。第一版按文件名升序取第一个，
   拿到的是最初那次失败解析（2 条没有编号的垃圾候选），于是把已 import 的 9 条报成「还没入账」。
   改成按 mtime 取最新，并按 `kind` 过滤（`draft` 与 `changelog` 的产物不混用）。
2. **低置信候选把待办淹了**。散话里捞的 0.35 分候选（`说明：避难层排风 = 50㎡`）天天出现在待办里，
   人会学会无视这条消息。改成 <0.6 不进待办；同时把「新条件」的置信度从 0.35 提到 0.80——
   `名称 = 值` 这种硬格式本身就说明它是条件，模板里没有不等于不可信。
3. **单位表缺 HVAC 的 `m³/h`**，`排风量 12000m³/h` 根本提不出来，文件被当成「没内容」。
   补了 `m³/h`、`m³`、`Pa`、`dB`、`℃`；顺带修了新条件的专业码取错
   （`[机电] 排风口净高` 曾因命中「净高」被归到结构，现在优先认方括号里的专业标签）。

### 实测

- `day.py --all --scan` 四个项目一次过：变更单项目 1 条提案、演示项目 1 条、演练项目 2 条、示例项目 1 份待确认资料。
- 新资料 `机电回复_2026-11-18.txt` → 2 条 0.80 候选入待办，`50㎡` 那句噪音被滤掉；确认后同一文件次日不再出现。
- launchd 改指向 `day.py --all --scan --notify`，`kickstart` 实测 `runs = 1 / last exit code = 0`，
  落盘 `state/daily/全部项目-2026-11-18.md`。
